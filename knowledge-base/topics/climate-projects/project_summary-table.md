# `modelled.project_summary` — Table Context

This document explains how to read and interpret rows from `modelled.project_summary`.
It is intended as context for AI-assisted data querying and interpretation.

Related: [`project_portfolio-table.md`](./project_portfolio-table.md) — the source catalog table that this enriches.

---

## Purpose

`project_summary` is an **AI-synthesised project profile**, generated by processing
the full text of a project's official documents (appraisal documents, implementation
reports, completion reports) through a structured extraction pipeline. It provides
a richer, more queryable version of the project record than the raw API metadata in
`project_portfolio`.

Each row in this table was produced by a GPT-4.1 model that read evidence extracted
from project documents and synthesised it into structured fields according to a fixed
schema. The synthesis is grounded strictly in document evidence — the model is
instructed to set any field to `null` if the documents do not support it, and to
never use general knowledge to fill gaps.

---

## ⚠️ Critical interpretation note: this data is AI-generated

All values in `project_summary` are the output of an AI model, not direct transcription
from a database or API. This has important implications:

- Fields may be `null` because the documents lacked evidence, not because the
  information doesn't exist
- Numeric values (budgets, emission reductions) are extracted from document text and
  may differ from the official figures in `project_portfolio`
- The `synthesis_notes` field flags known conflicts, uncertain inferences, and fields
  that should be verified by a human
- The `data_completeness` JSON field indicates which key fields were populated
- Always check `evidence_anchors` to understand which document and page a value came from

When precision matters, verify values against the source document or `project_portfolio`.

## Schema

### Scalar fields

| Column | Type | Description |
|---|---|---|
| `project_summary_id` | uuid (PK) | Deterministically derived from `world_bank-{source_project_id}-project_summary` |
| `project_id` | uuid | FK to `modelled.project_portfolio` |
| `source_project_id` | varchar | Funder's own project ID (e.g. `P006634`) |
| `project_title` | text | Project title from synthesis (may differ slightly from `project_portfolio.project_name`) |
| `funder_id` | varchar | Normalised funder identifier (e.g. `world_bank`) |
| `funder_name` | varchar | Human-readable funder name |
| `country_name` | varchar | Country as extracted from documents |
| `country_code` | varchar | ISO 3166-1 alpha-2 |
| `region_name` | varchar | Sub-national region if stated in documents (not funder's regional grouping) |
| `city_name` | varchar | City if the project is city-specific |
| `project_type` | varchar | Inferred project type (see values below) |
| `sector_name` | varchar | Normalised sector (see values below) |
| `subsector_name` | varchar | Specific subsector (e.g. `solar_pv`, `brt`, `waste_to_energy`) |
| `approval_at` | datetime | Approval date from documents |
| `closing_at` | datetime | Closing date from documents |
| `project_status` | varchar | Normalised status (see values below) |
| `total_budget_amount_usd` | decimal | Total project budget in USD, from documents |
| `primary_funder_amount_usd` | decimal | Funder's own contribution in USD |
| `financing_instrument` | varchar | Normalised instrument type (see values below) |
| `project_summary_text` | text | 2–3 sentence narrative: what was done, where, and what it achieved |
| `lessons_learned` | text | Documented lessons from the project, if available |
| `synthesis_notes` | text | Flags from the model: conflicts, uncertain inferences, review recommendations |
| `release_id` | uuid | FK to `modelled.dataset_release` |
| `created_at` / `updated_at` | datetime | Row timestamps |

### JSON fields

All JSON fields are described in detail below.

| Column | JSON type | Description |
|---|---|---|
| `site_context` | object | Location, terrain, and infrastructure context |
| `financing_structure` | object | Breakdown of funding sources by type |
| `data_completeness` | object | Flags indicating which key fields were populated |
| `actions_implemented` | array | List of discrete interventions with scale and status |
| `key_risks` | array | Identified risks by type |
| `evidence_anchors` | array | Source citations backing numeric and key fields |
| `secondary_project_types` | array | Additional project types if genuinely mixed |
| `co_financiers` | array | Confirmed co-financing organisations |
| `co_benefits` | array | Non-emissions co-benefits |
| `key_interventions` | array | High-level list of project components |
| `replicability_conditions` | array | Prerequisites for replicating this project elsewhere |
| `model_metadata` | object | Provenance: model, generation time, atom counts |

## JSON field reference

### `site_context`

Describes the physical and infrastructural setting of the project.

```json
{
  "geography": "Urban corridor connecting São Paulo city centre to the western suburbs",
  "resourceConditions": "High traffic volume on existing road network; BRT corridor feasibility confirmed",
  "infrastructureContext": "Existing road right-of-way available; municipal bus operator in place",
  "environmentalConditions": "Tropical climate with heavy wet season; flooding risk on two sections",
  "notes": null
}
```

All sub-fields can be `null`. Useful for filtering projects by physical context
(e.g. coastal, arid, urban/rural) or infrastructure prerequisites.

---

### `financing_structure`

Breaks down the project budget by funding type as proportions (0–1).

```json
{
  "grant_pct": 0.15,
  "loan_pct": 0.60,
  "private_pct": null,
  "government_pct": 0.25,
  "notes": "Grant component is GEF contribution. Government share is counterpart funding from Ministry of Finance. Private share not stated in documents."
}
```

- Proportions may be explicitly stated or computed by the model from component amounts
- If computed, the derivation is described in `notes`
- Proportions may not sum to exactly 1.0 if some components are uncertain
- All proportions `null` indicates insufficient financing detail in documents

---

### `data_completeness`

A quality flag object indicating which key fields were populated. Use this to quickly
assess how useful a summary row will be for a given analysis.

```json
{
  "hasCapacityData": true,
  "hasEmissionReductionData": false,
  "hasFinancingStructure": true,
  "hasSiteContext": true,
  "hasActionsImplemented": true,
  "missingKeyFields": ["totalEmissionReductionTco2e", "mrvApproach", "lessonsLearned"]
}
```

`missingKeyFields` lists specific fields that are `null` but would normally be expected
for a project of this type. It is the first thing to check when a summary appears
incomplete.

---

### `actions_implemented`

A list of discrete interventions with scale and implementation status.

```json
[
  {
    "action": "Construction of 32 km BRT corridor",
    "scale": "32 km of dedicated busway",
    "status": "completed"
  },
  {
    "action": "Fleet renewal with 120 articulated buses",
    "scale": "120 buses",
    "status": "completed"
  },
  {
    "action": "Integrated fare payment system",
    "scale": null,
    "status": "in_progress"
  }
]
```

Each item maps to one discrete thing that was built or changed. This is the most
useful field for understanding what a project actually did, independently of its
headline description.

`status` values: `planned` | `in_progress` | `completed`

---

### `key_risks`

Identified risks categorised by type.

```json
[
  {
    "type": "construction",
    "risk": "Land acquisition delays for two sections of the BRT corridor"
  },
  {
    "type": "governance",
    "risk": "Coordination required across three municipal authorities"
  }
]
```

Risk types: `construction` | `market` | `resource` | `governance` | `reversal` | `regulatory` | `social` | `capacity`

---

### `evidence_anchors`

Citations backing each numeric or key field. This is the primary traceability mechanism —
it links a summary field value back to the specific page and document where the evidence
was found.

```json
[
  {
    "field": "totalBudgetUsd",
    "claim": "Total project cost is USD 850M including co-financing",
    "pageOrSection": "Page 12, Project Cost and Financing table",
    "sourceName": "P006634_PAD.pdf",
    "evidenceKind": "quantitative"
  },
  {
    "field": "actionsImplemented",
    "claim": "32 km BRT corridor constructed and operational",
    "pageOrSection": "Section 3.2, Physical Outputs",
    "sourceName": "P006634_ICR.pdf",
    "evidenceKind": "quantitative"
  }
]
```

`evidenceKind`: `quantitative` | `qualitative` | `categorical`

When a value looks surprising or needs verification, locate the relevant anchor by
matching `field` to the column name and follow the `sourceName` reference.

---

### `replicability_conditions`

Prerequisites for replicating this project in another city or country. These are
physical and infrastructure conditions, not generic governance statements.

```json
[
  "City population above 500,000",
  "Existing road corridor with right-of-way available",
  "Municipal bus operator with maintenance capacity",
  "National or state government counterpart funding commitment"
]
```

These are inferred by the model from the project's documented context and challenges.
They are useful for action recommendation — matching a target city's conditions against
a proven project archetype.

---

### `co_benefits`

Non-emissions benefits documented in project evidence.

```json
["air_quality", "jobs", "public_health", "mobility"]
```

Possible values: `air_quality` | `jobs` | `biodiversity` | `public_health` | `energy_security` | `water_security`

---

### `model_metadata`

Provenance information for the synthesis process.

```json
{
  "generated_at": "2026-04-09T14:23:11+00:00",
  "source_project_id": "P006634",
  "selected_atoms_count": 87,
  "raw_atoms_count": 312,
  "model": "gpt-4.1"
}
```

| Field | Meaning |
|---|---|
| `generated_at` | UTC timestamp of synthesis |
| `source_project_id` | Cross-check with `project_summary.source_project_id` |
| `selected_atoms_count` | Evidence chunks passed to the model (after quality filtering) |
| `raw_atoms_count` | Total evidence chunks extracted from documents before filtering |
| `model` | LLM used for synthesis |

Low `selected_atoms_count` (e.g. < 10) may indicate limited document coverage and
correlates with higher rates of `null` fields. Check `data_completeness` when
`selected_atoms_count` is low.

## How the data was produced

The `project_summary` pipeline has several stages:

1. **Project discovery** — World Bank Projects API queried for climate-tagged projects; results stored in `project_portfolio`
2. **Document retrieval** — Project document PDFs fetched from the World Bank Documents API for each project in `project_portfolio`
3. **Atom extraction** — Each PDF is converted to markdown and chunked into evidence "atoms" — structured units of evidence with fields like `primitive_type`, `raw_value_numeric`, `evidence_kind`, and `page_or_section`
4. **Atom selection** — Atoms are ranked by document type priority (completion reports > implementation status > appraisals) and evidence quality (quantitative > qualitative), then capped by type to fit model context
5. **Synthesis** — GPT-4.1 receives the project catalog record and selected atoms and produces the structured JSON output that populates this table
6. **Upsert** — Results written to `project_summary` via SQL upsert; existing rows updated if re-synthesised

The synthesis prompt enforces strict evidence-only rules: no general knowledge, `null`
for unsupported fields, explicit evidence anchors for all numeric values.

## Common query patterns

**Projects with emission reduction data, by sector:**
```sql
SELECT project_title, country_name, sector_name,
       (data_completeness->>'hasEmissionReductionData')::boolean AS has_emissions,
       total_budget_amount_usd
FROM modelled.project_summary
WHERE (data_completeness->>'hasEmissionReductionData')::boolean = true
ORDER BY total_budget_amount_usd DESC NULLS LAST;
```

**Projects with BRT or bus interventions:**
```sql
SELECT project_title, country_name, city_name, project_summary_text
FROM modelled.project_summary
WHERE subsector_name = 'brt'
   OR project_summary_text ILIKE '%bus rapid transit%';
```

**Unpack actions for a single project:**
```sql
SELECT
  project_title,
  action_item->>'action' AS action,
  action_item->>'scale'  AS scale,
  action_item->>'status' AS status
FROM modelled.project_summary,
     LATERAL jsonb_array_elements(actions_implemented) AS action_item
WHERE source_project_id = 'P006634';
```

**Find projects with incomplete synthesis (few atoms):**
```sql
SELECT source_project_id, project_title,
       (model_metadata->>'selected_atoms_count')::int AS atoms,
       data_completeness->>'missingKeyFields' AS missing
FROM modelled.project_summary
WHERE (model_metadata->>'selected_atoms_count')::int < 10
ORDER BY atoms;
```
